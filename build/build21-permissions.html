The thing that was actually breaking

Here is the part worth knowing. The switch in that list has been reading on the whole time, while the app was being refused permission anyway. That isn't a bug in the list — it's how macOS records permissions, and it was being tripped by how I was building the app.

A permission is stored against the app's signature. The builds I'd been giving you were signed “ad-hoc”, which means the recorded signature is a fingerprint of that exact build. Rebuild the app and the fingerprint changes — so the permission stops matching, while the switch carries on saying “on”. Remove-and-re-add fixed it, until the next build wiped it out again. That is why this kept coming back.

What changed — and the proof it worked

The app is now signed with your real Apple Development certificate rather than ad-hoc. I found it already sitting in your keychain — the project was configured with the wrong team ID, which is why builds had been quietly falling back to ad-hoc all along. The permission is now tied to the certificate instead of the build, so this should be the last time you ever have to grant it.

Confirmed, not assumed: build 22 was installed over build 21 a few minutes later, and it came up with its event tap already working — no re-grant, no alert. Build 23 repeated the same test with the same result. That is precisely the thing that used to break on every single build.

Build 23 also closed a related hole. The older check the app used to decide "is the permission missing?" asked macOS a question that answers yes even when the answer is no — so it would have stayed quiet in exactly the situation it existed for. It now asks the real question, so if this ever goes wrong again the app will tell you instead of silently doing nothing.

What to do — once

  1. Open Privacy & Security The app is showing you an alert right now with a button that takes you straight there. Or do it by hand from System Settings.
  2. Choose “Device Control and Data Access” In the list of permissions. Scroll — it sits between the media and screen-recording entries.
  3. Select XDRMonitorControl and press – This clears the old, stale record. The switch being on does not mean it works.
  4. Press + and add it back Navigate to Applications and pick XDRMonitorControl. Make sure the switch is on afterwards.
  5. Quit and reopen the app Then the hardware brightness and volume keys should drive the monitors again.
Note

The keys only do anything when a monitor is actually connected — with nothing plugged in the app deliberately stays out of the way and lets macOS handle the volume itself. So test it docked.

Smooth volume control

The volume keys were jumping 6% at a time. That wasn't a bug so much as an unlucky default: the app rounds each press to the nearest block on the on-screen volume display, and that display has 16 blocks — so one press moved 1/16 of the range, 6.25%, which lands as 6.

The app already has the answer built in, as a checkbox in Settings → Keyboard called “Use fine OSD scale for volume”. It was simply off. Turning it on moves the volume 1% per press and redraws the on-screen indicator with 100 blocks to match. I've made it the default.

Worth knowing

Holding Option+Shift while pressing now gives you the old coarse jump, so you still have a fast sweep when you want one. It's the reverse of how it worked before.

And if 1% ever feels too slow, untick that checkbox in Settings → Keyboard and you're back to 16 steps.
